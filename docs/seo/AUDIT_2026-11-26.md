## 2. Architecture évaluée

Le site est un **multipage statique** : chaque page publique est un fichier HTML complet, généré au commit par `tools/build-public-site.mjs` et `tools/build-public-docs.mjs`, copié dans `dist/` par `tools/build-public.mjs`. Le contenu essentiel est dans le HTML brut, avant tout script : il n'existe ni repli SPA (la dernière règle répond `/* → /404.html 404`), ni dépendance à une session. Les pages publiques ne chargent que `pwa.js`, `passage.js` et `ga4-consent.js`, ainsi que le script RUM que Netlify injecte. Elles ne chargent ni Supabase, ni bundle applicatif, ni carte, ni SDK publicitaire. Les écrans de l'application sont des pages séparées, en `noindex`, qui chargent le shell et Supabase.

**Décision : aucun découplage supplémentaire.** Pré-rendu, SSR, seconde application ou second domaine n'apporteraient rien : la vitrine est déjà découplée. Le risque réel était l'**absence de garde-fou** contre une régression. Le découplage est donc verrouillé par contrat :
- liste fermée des scripts autorisés sur une page publique (`scripts-added`) ;
- budget de poids par page (`weight-regression`) ;
- contrôle rendu sans Supabase ni Google (`seo-render`).
